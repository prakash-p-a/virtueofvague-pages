CVE-2026-82533 let a confined coding agent turn off its own sandbox with one command, because the control interface trusted a header the caller writes.

issue 3 · 5 oct 2026

the door that said yes: an agent switches off its own sandbox

Half my feed this week arrived with the energy of a WhatsApp message marked “forwarded many times”. Rogue agents, regulators, training pauses. Loud, and hard to trace to a source.

So the filter this week is simple: only the story with a paper trail.

the tell

DeepSeek Harness is an open-source runtime for AI coding agents. In September it got CVE-2026-82533, scored 9.4 by VulnCheck. The Hacker News describes it plainly: a sandboxed agent could switch off its own sandbox.

The mechanism is almost boring. The tool ran a local web interface for managing sessions. That interface decided who was calling by reading the Host header, which is a value the caller writes itself. A header is not an auth layer. So one shell command from inside the sandbox could ask the interface to set the session to “danger-full-access”, with approval prompts gone.

My read: nobody broke the walls. The agent asked the door, and the door believed what it was told. Not the model weights. The plumbing.

what i’m ignoring

  • The “rogue agents” and regulator headlines. Widely forwarded, and I could not trace them to a regulator’s own statement or a lab’s own disclosure. Until the primary document shows up, that is a story about a story.
  • “Which AI model is best” rankings. The answer depends on who is asking, and the ranking rarely says who.
  • Agent sandbox explainers that end in a product pitch. Vendor claims, unverified.

the real one

The fix is the useful part. Per the coverage, the Host-header check was replaced with token auth: the tool prints a one-time token at startup, and the browser swaps it for a signed cookie. A caller now has to hold something, not just say something.

That pattern travels. You can ask the same question of any agent runtime you run.

What I’d watch:

  • a local control port that the agent can reach from inside its own sandbox
  • any trust decision made from a header or field the caller can set
  • desktop apps that bundle the harness and carry the old version quietly

Caveat: this is one product, already patched, and my account of the mechanism comes from write-ups, not from reading the code. OX Security’s write-up says the sandbox blocked file writes but left local networking open. I would treat the class of bug as the signal, not this one CVE.

the part that stays

Security angle: the cage and the keys sat in the same room. A local control plane is convenient. It is also the place where blast radius lives, and convenience and blast radius are the same coin.

Human angle: we say “the agent went rogue”. Here nobody went anywhere. The agent did something the design allowed. Accountability for that sits with whoever shipped the default and whoever approved it.

Honestly? I don’t know how many other runtimes have the same gap. I haven’t seen anyone count.

do this week

  1. List where coding agents run in your environment, laptops included. For each one, ask a single question: can the agent reach the thing that sets its own permissions?
  2. If you use DeepSeek Harness, or an app that wraps it, check the version is 0.1.2-alpha.2 or later.

Which of your agents has the shortest walk from its cage to its keys?
